# 城市资源一张图可视化需求文档

> 版本：v1.1  
> 日期：2026-05-21  
> 状态：修订版

---

## 1. 项目概述

### 1.1 项目背景

当前城市管理面临资源分散、数据孤岛、底数不清等问题。各类城市资源的空间分布、运行状态、关联关系缺乏统一的可视化呈现手段，导致城市管理者难以快速掌握全局态势、精准调度资源、科学辅助决策。

建设**城市资源一张图**系统，以 GIS 地图为载体，整合城市建筑、市政、安防、生态、人口与网格五大类资源数据，实现"一图揽全局、数据可穿透、态势可感知、资源可调度"的目标。

### 1.2 建设目标

| 目标 | 说明 |
|------|------|
| **底数清** | 全域资源数据的空间化、结构化、标准化汇聚，消除数据盲区 |
| **情况明** | 资源实时状态可视、历史趋势可溯、异常变化可知 |
| **管得住** | 基于空间位置的资源关联查询、统计分析和预警调度 |
| **服务好** | 为城市规划、应急指挥、公共服务提供数据底座和可视化能力 |

### 1.3 建设原则

- **一图统览**：所有资源以地理空间为索引，统一在一张地图上分层呈现
- **数据驱动**：以真实数据驱动可视化，不展示无数据支撑的虚拟内容
- **分层分级**：按资源类型分层、按行政区域分级，支持下钻与上卷
- **动静结合**：静态基础信息与动态运行状态融合展示

## 2. 总体架构

### 2.1 系统分层架构

```
┌──────────────────────────────────────────────────────┐
│                   应用呈现层                           │
│  GIS Map | 告警中心 UI | 综合大屏 | 第三方 API 调用   │
│  ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐ ┌──────────┐  │
│  │建筑  │ │市政  │ │安防  │ │生态  │ │人口与网格 │  │
│  │资源  │ │资源  │ │资源  │ │资源  │ │  资源    │  │
│  └──────┘ └──────┘ └──────┘ └──────┘ └──────────┘  │
├──────────────────────────────────────────────────────┤
│              API 网关层                               │
│  REST API (OpenAPI 3.0) | WebSocket | OAuth2 认证鉴权 │
├──────────────────────────────────────────────────────┤
│              业务服务层                               │
│  资源查询 | 空间分析 | 统计聚合 | 告警规则引擎        │
│  通知推送 (短信/语音/弹窗) | 数据导出 | 报表服务      │
├──────────────────────────────────────────────────────┤
│              消息与流处理层                           │
│  规则实时评估 (Kafka Streams) | 消息队列 | 事件总线   │
├──────────────────────────────────────────────────────┤
│              数据存储层                               │
│  空间数据(PostGIS) | 业务数据 | 时序库 | 缓存(Redis)  │
├──────────────────────────────────────────────────────┤
│              数据接入层                               │
│  ETL调度 | MQTT Broker | 批量文件导入 | 第三方API对接 │
└──────────────────────────────────────────────────────┘
```

### 2.2 技术指标

| 指标 | 要求 |
|------|------|
| 地图加载 | 首屏 < 3 秒，瓦片加载 < 1 秒 |
| 资源点位渲染 | 10 万级点位流畅交互 |
| 数据刷新 | 静态数据 T+1，动态数据 ≤ 30 秒 |
| 图层切换 | 图层开关响应 < 500ms |
| 空间查询 | 多边形/缓冲区查询 < 3 秒 |
| 并发支持 | 支持 ≥ 200 用户同时在线 |

## 3. 功能需求

### 3.1 通用地图能力

所有资源模块共享以下基础地图能力：

| 能力 | 详细要求 |
|------|---------|
| 底图切换 | 支持卫星图、矢量图、路网图切换 |
| 缩放平移 | 1-18 级缩放，支持鼠标/触控 |
| 图层控制 | 独立开关各资源图层，支持透明度调节 |
| 区域定位 | 行政区划树形选择、经纬度定位、关键字搜索定位 |
| 测距测面 | 地图上的距离和面积测量工具 |
| 标绘工具 | 点标记、线绘制、面绘制、文字标注 |
| 分屏对比 | 支持同一区域不同时段/不同图层分屏对比 |
| 全屏模式 | 一键全屏沉浸式展示 |
| 数据时效标注 | 每个资源点位上显示数据更新时间戳或"X 天前更新"标签，便于使用者判断数据新鲜度 |
| 数据来源标识 | 区分"IoT 实时" / "系统对接" / "人工录入" / "推算预估"，用不同标识色或图标，提升数据可信度透明度 |

### 3.2 建筑资源模块

#### 3.2.1 全域楼栋信息

- **楼栋分布热力**：以热力图展示全域建筑密度分布
- **楼栋属性面板**：点击楼栋弹出详情卡片，包含：
  - 基础信息：楼栋编号、名称、地址、建筑年代、产权单位
  - 建筑指标：占地面积、总建筑面积、层数（地上/地下）、建筑高度、结构类型
  - 功能属性：建筑用途（住宅/商业/办公/工业/公共设施/混合）
- **三维白模**：基于楼栋高度和轮廓数据，生成三维白模，支持旋转查看
- **条件筛选**：按区域、用途、建筑面积区间、建筑年代区间筛选高亮

#### 3.2.2 楼层结构与用途

- **楼层剖分**：选中楼栋后展示楼层剖面图，每层用色块标识用途
- **用途分布**：饼图/柱状图统计全域建筑用途占比（住宅 vs 商业 vs 办公等）
- **面积统计**：按街道/社区维度统计各类用途建筑面积汇总
- **垂直分层**：显示每层的功能分区（商铺、办公、居住、设备层、停车场等）

#### 3.2.3 人员入驻情况

- **入驻概览**：楼栋/楼层级入驻率展示（已入驻面积 / 可租售面积）
- **企业分布**：楼栋内入驻企业列表及空间位置标注
- **人员密度**：基于常住/办公人口估算的楼栋人员密度热力

#### 3.2.4 数据字段清单

| 字段 | 类型 | 说明 |
|------|------|------|
| building_id | string | 楼栋唯一编码 |
| building_name | string | 楼栋名称 |
| address | string | 详细地址 |
| district / street / community | string | 所属区/街道/社区 |
| total_area | float | 总建筑面积(㎡) |
| floor_count | int | 总层数 |
| underground_floors | int | 地下层数 |
| building_height | float | 建筑高度(m) |
| structure_type | enum | 结构类型(钢混/砖混/钢结构等) |
| build_year | int | 建成年份 |
| use_type | enum | 建筑用途 |
| occupancy_rate | float | 入驻率(%) |
| coordinates | GeoJSON | 楼栋轮廓坐标 |

### 3.3 市政资源模块

#### 3.3.1 道路

- **路网可视化**：按道路等级（快速路/主干道/次干道/支路）分级着色展示
- **道路详情**：名称、长度、宽度、车道数、起止点、养护状态、最近维修时间
- **交通状态**：接入实时交通数据，路段颜色反映拥堵程度（绿/黄/红）
- **路长信息**：显示对应路段的负责人、联系方式、巡查记录

##### 道路核心数据字段

| 字段 | 类型 | 说明 |
|------|------|------|
| road_id | string | 道路唯一编码 |
| road_name | string | 道路名称 |
| road_level | enum | 等级（快速路/主干道/次干道/支路） |
| length | float | 长度(m) |
| width | float | 红线宽度(m) |
| lane_count | int | 车道数 |
| start_point | string | 起点名称 |
| end_point | string | 终点名称 |
| maintenance_status | enum | 养护状态（良好/一般/破损/大修） |
| road_manager | string | 路长姓名 |
| coordinates | GeoJSON | 道路中心线坐标 |

#### 3.3.2 桥梁

- **点位标记**：桥梁点位图标标记，按安全等级用颜色区分
- **桥梁详情**：名称、类型（梁桥/拱桥/悬索桥等）、全长、桥宽、设计荷载、建造年份、最近检测日期、安全等级
- **检测记录**：时间线展示历次检测结果和维修记录

#### 3.3.3 路灯

- **分布可视化**：沿道路线状分布的路灯点位
- **设备状态**：在线/离线/故障三态颜色标识
- **远程控制**：支持单灯/群控开关和调光（含操作记录）
- **能耗统计**：按区域/时间维度的能耗汇总图表

#### 3.3.4 井盖

- **点位分布**：各类型井盖（雨水/污水/电力/通信/燃气/热力）分类符号展示
- **状态监控**：正常/异常开启/破损/丢失状态
- **告警管理**：异常开启、水位超限实时告警弹窗和列表
- **巡检记录**：关联井盖巡检历史和养护工单

#### 3.3.5 管网

- **管网拓扑**：地下管线的线状网络可视化，按管类（给水/排水/燃气/电力/通信/热力）分色
- **管点标注**：阀门、检查井、泵站等附属设施点位
- **横断面视图**：道路横断面展示各类管线的埋深、管径、相对位置
- **爆管分析**：模拟关闭阀门影响范围（上游/下游关阀分析）

#### 3.3.6 充电桩

- **点位分布**：充电桩点位聚合/散点展示，按类型（快充/慢充）区分图标
- **实时状态**：空闲/占用/故障/离线状态轮播显示
- **使用统计**：充电次数、充电量、使用率按日/周/月统计
- **运营数据**：各运营商（国网/特来电/星星充电等）的桩数及占比

#### 3.3.7 环卫设施

- **设施分布**：公厕、垃圾中转站、垃圾箱/桶、环卫车辆停车场点位标注
- **公厕详情**：名称、地址、厕位数量、开放时间、卫生评级、人流量
- **环卫车辆**：车辆实时位置追踪，作业轨迹回放
- **满溢告警**：智能垃圾桶满溢状态实时告警

### 3.4 安防资源模块

#### 3.4.1 摄像头

- **点位分布**：监控摄像头点位图标标注，按类型（枪机/球机/半球/全景）分类
- **在线状态**：在线/离线/故障状态色标
- **视频预览**：点击点位弹出视频流预览窗口（支持 RTSP/GB28181）
- **覆盖分析**：基于摄像头朝向和可视半径绘制覆盖区域热力图，识别监控盲区
- **AI 事件**：关联视频 AI 分析事件（人员聚集、异常滞留、入侵检测等）

##### 摄像头核心数据字段

| 字段 | 类型 | 说明 |
|------|------|------|
| camera_id | string | 摄像头唯一编码 |
| camera_name | string | 摄像头名称 |
| camera_type | enum | 类型（枪机/球机/半球/全景/云台） |
| resolution | string | 分辨率（如 1080P/4K） |
| install_height | float | 安装高度(m) |
| direction | float | 朝向角度(°) |
| focal_length | float | 焦距(mm) |
| ip_address | string | IP 地址 |
| stream_url | string | 视频流地址 |
| protocol | enum | 协议类型（RTSP/GB28181/ONVIF） |
| storage_days | int | 存储天数 |
| ai_capability | string[] | AI 能力（人脸/车牌/烟火/聚集等） |
| online_status | enum | 在线状态（在线/离线/故障） |
| coordinates | GeoJSON | 安装点位坐标 |

#### 3.4.2 卡口

- **点位分布**：治安卡口、交通卡口点位标注
- **过车数据**：按时间/车牌/车道查询过车记录，轨迹回放
- **布控管理**：布控车辆名单管理，实时比对告警
- **统计报表**：车流量按日/周/月/年统计趋势

#### 3.4.3 门禁

- **点位分布**：小区/楼宇门禁点位标注
- **通行记录**：按时间/人员/门禁点查询通行记录
- **异常告警**：非法刷卡、多次尝试失败、门未关严等告警

#### 3.4.4 岗点与巡逻路线

- **岗点分布**：固定岗、值守点、警务站点位标注，含执勤人员信息和联系方式
- **巡逻路线**：预设巡逻路线在地图上的线状展示，含巡逻段编号、长度、预计时长
- **巡逻轨迹**：巡逻人员/车辆的实时 GPS 轨迹回放
- **到岗率**：各岗点在岗情况统计，脱岗/离岗告警

### 3.5 生态资源模块

#### 3.5.1 空气质量

- **监测站点**：国控/省控/市控空气质量监测站点位
- **实时数据**：AQI、PM2.5、PM10、O₃、NO₂、SO₂、CO 实时数值
- **空间插值**：基于监测站点数据生成全域空气质量插值分布图
- **历史趋势**：各指标 24 小时/7 天/30 天趋势曲线
- **预警发布**：污染预警等级标识和影响范围标注

#### 3.5.2 水质

- **监测断面**：河流/湖泊水质监测断面点位标注
- **水质类别**：I~V 类水分色展示，劣 V 类高亮告警
- **实时指标**：溶解氧、COD、氨氮、总磷、PH 等实时数据
- **污染溯源**：沿河污染源定位和上下游关联分析
- **黑臭水体**：识别和标注黑臭水体位置及治理状态

#### 3.5.3 噪声

- **监测点位**：功能区噪声监测点、交通噪声监测点位标注
- **实时分贝**：各点位实时噪声值，彩色圆形辐射图展示
- **噪声地图**：基于监测数据生成区域噪声分布热力图（昼间/夜间）
- **超标告警**：超阈值自动告警，支持按区域/时段统计超标频次

#### 3.5.4 绿化覆盖

- **绿地分布**：公园绿地、防护绿地、广场绿地、附属绿地面状展示
- **绿化率统计**：按行政区/街道统计绿化覆盖率
- **植被类型**：乔/灌/草分类标注
- **古树名木**：古树点位标注，含树种、树龄、保护等级、养护记录
- **遥感对比**：多期卫星影像对比，展示绿化变化

#### 3.5.5 污染源分布

- **固定污染源**：工业企业的废气/废水/固废排放口点位标注
- **移动污染源**：高排放车辆热点区域
- **面源污染**：农业面源、工地扬尘区域标注
- **排放监控**：重点排污单位在线监测数据实时接入
- **环保档案**：企业环保审批、排放许可、处罚记录关联查询

### 3.6 人口与网格资源模块

#### 3.6.1 网格划分

- **网格边界**：以面图层展示综合网格、专属网格的边界划分
- **网格编码**：显示网格编码、四至范围、面积
- **网格员信息**：网格长、专职网格员、兼职网格员的姓名、电话、管辖范围
- **网格画像**：网格人口数、房屋数、企业数、重点场所数的概览统计仪表盘

#### 3.6.2 实有人口

- **人口热力**：基于实有人口数据的人口密度网格热力图
- **人口结构**：年龄金字塔、性别比、户籍/非户籍比例饼图
- **人户关联**：点击楼栋显示户数和人口数，下钻至户成员列表
- **流动人口**：流动人口分布、来源地分析、停留时长统计
- **人口变化**：近 6 个月/1 年的人口增减趋势

#### 3.6.3 特殊人群

- **分类标注**：老年人（60+）、残疾人、低保户、重点关爱人群分类标注
- **分布热力**：特殊人群空间聚集度分析
- **帮扶记录**：走访记录、帮扶措施、物资发放历史
- **重点关注**：高风险/高关怀人员的重点关注标记和预警机制

#### 3.6.4 重点场所标注

- **场所分类**：
  - 教育类：学校、幼儿园、培训机构
  - 医疗类：医院、社区卫生服务站、药店
  - 商业类：商场、超市、农贸市场
  - 文体类：体育馆、图书馆、文化馆
  - 宗教类：寺庙、教堂
  - 危化品类：加油站、燃气站、化工厂
- **场所详情**：名称、地址、负责人、联系方式、面积、核定人数
- **安全关联**：关联场所附近的摄像头、消防设施、安防岗点
- **人流监测**：接入重点场所人流量数据，超阈值预警

### 3.7 跨资源关联分析

"一张图"的核心价值在于打通资源类型界限，实现跨域关联查询。以下是主要跨资源关联场景：

#### 3.7.1 人-房-企业关联

| 关联路径 | 查询示例 |
|---------|---------|
| 楼栋 → 人口 | 选中楼栋 → 展示该楼栋实有人口总数、年龄结构、户籍/流动比例 |
| 楼栋 → 企业 | 选中楼栋 → 展示入驻企业列表、员工数、行业分布 |
| 网格 → 人房企 | 选中网格 → 展示网格内房屋总数、实有人口、企业数 |
| 人员 → 活动热力（脱敏） | 脱敏聚合展示居住地-工作地-常活动区域的人员分布热力 |

#### 3.7.2 事件-资源联动

- **告警关联**：摄像头 AI 告警 → 自动定位最近岗点、显示网格员联系方式、调取周边 500m 内摄像头画面
- **应急调度**：爆管/火灾事件 → 高亮最近消防栓、执行关阀模拟、规划最优救援路径
- **污染溯源**：水质断面超标 → 逆流追溯上游排污口、显示对应企业环保档案

#### 3.7.3 场所-安防关联

- 选中学校/医院等重点场所 → 自动聚合周边摄像头、卡口、门禁、岗点信息

- **一屏统览**：五大类资源核心指标在同一仪表盘聚合展示
- **跨域统计**：如"某街道实有人口 X 万，楼栋 X 栋，摄像头 X 路"的聚合摘要
- **下钻联动**：综合看板点击某街道 → 地图定位至该街道 → 各图层同步过滤

### 3.8 告警规则引擎

> **说明**：告警规则引擎是跨模块通用能力，贯穿建筑、市政、安防、生态、人口与网格五大资源类型。告警中心 UI 可通过顶部工具栏从任意模块进入，无需在模块内重复建设。

当前文档各模块中独立定义了"告警"能力（井盖异常、垃圾桶满溢、水质超标、卡口布控等），但缺乏统一的告警规则定义、触发、通知和闭环管理机制。本节作为跨模块的通用能力，定义告警规则引擎的完整规范。

#### 3.8.1 规则类型

告警规则按触发逻辑分为四类：

| 类型 | 说明 | 适用场景 |
|------|------|---------|
| **阈值规则** | 监测值超过/低于固定阈值时触发 | 水位超限、pH 超标、气体浓度报警 |
| **基线规则** | 监测值偏离历史基线（同比/环比/滑动窗口）时触发 | 用水量突增、车流量异常下降 |
| **事件规则** | 特定事件发生时触发 | 井盖异常开启、卡口布控车辆通过、摄像头 AI 告警 |
| **复合规则** | 多个条件组合（AND/OR/NOT）触发 | 水位超限 AND 同一井盖异常开启 → 管道爆裂高概率告警 |

#### 3.8.2 规则定义结构

每条告警规则包含以下字段：

```json
{
  "ruleId": "string",
  "ruleName": "string",
  "resourceType": "string",
  "ruleType": "threshold|baseline|event|composite",
  "enabled": true,
  "priority": "low|medium|high|critical",
  "conditions": [
    {
      "metric": "water_level",
      "operator": ">",
      "value": 0.8,
      "unit": "m",
      "duration": 30
    }
  ],
  "logic": "AND",
  "evalInterval": 60,
  "notifyChannels": ["popup", "sms", "app"],
  "notifyRoles": ["grid_worker", "supervisor"],
  "escalationDelay": 300,
  "autoRecover": true,
  "mutePeriods": [
    {"start": "22:00", "end": "07:00", "muteBelow": "critical"}
  ]
}
```

#### 3.8.3 告警级别与颜色规范

| 级别 | 颜色 | 响应要求 | 示例 |
|------|------|---------|------|
| **提示 (Info)** | 蓝色 #1890FF | 仅记录，无需处理 | 垃圾桶容量达 80%、井盖开启但未超阈值 |
| **一般 (Low)** | 黄色 #FAAD14 | 30 分钟内确认 | 垃圾桶满溢、井盖状态异常 |
| **重要 (High)** | 橙色 #FA541C | 10 分钟内确认并处置 | 水位超限、水质超标、设备离线 > 1h |
| **严重 (Critical)** | 红色 #F5222D | 5 分钟内确认并启动应急 | 管道爆裂告警（复合规则命中）、消防通道占用、布控车辆通行 |

> 地图上告警点位按级别显示为对应颜色的呼吸动画图标，严重级别图标尺寸为一般级别的 1.5 倍。

#### 3.8.4 告警生命周期

每条告警经历以下完整状态机：

```
产生 → 待确认 → 处置中 → 已闭环
                    │               ↑
                    └── 超时未确认 ──┘
                           ↓
                     升级告警（通知上级角色）
```

| 状态 | 含义 | 触发动作 |
|------|------|---------|
| **产生** | 规则条件命中，生成告警记录 | 写入告警表；按配置推送通知；地图上对应点位闪烁 |
| **待确认** | 已通知但无人签收 | 倒计时 escalationDelay；超时未确认自动升级 |
| **处置中** | 责任人已签收，正在处理 | 在地图上显示处置轨迹/关联工单号 |
| **已闭环** | 告警原因已消除或人工关闭 | 停止闪烁；记录闭环时间和处置结论；归入告警历史 |
| **自动恢复** | 监测值回到正常范围，规则不再命中 | 无需人工确认，自动标记为已闭环（autoRecover=true 时） |

#### 3.8.5 通知渠道与策略

| 渠道 | 适用级别 | 实现方式 |
|------|---------|---------|
| **弹窗告警** | Low / High / Critical | WebSocket 实时推送，地图右上方弹出告警卡片，可点击定位到点位 |
| **站内信** | 全部级别 | 告警中心统一列表，支持按状态/级别/时间筛选 |
| **短信通知** | High / Critical（可配置） | 对接第三方短信网关，仅发送给当值责任人 |
| **语音呼叫** | Critical 仅 | 对接语音通知服务（如云呼叫中心），自动拨打责任人电话 |
| **App 推送** | 全部级别 | 移动端 Push Notification（移动端二期功能，需预留接口） |

> **防重复策略**：同一资源点位同一规则在防重复窗口内重复触发不重复通知（默认 30 分钟，可配置），仅更新告警记录中的"最近触发时间"和"触发次数"。
>
> **静音时段**：支持按规则配置静音时段（如 22:00-07:00 仅 Critical 级别触发语音呼叫，其余级别仅记录不通知）。

#### 3.8.8 性能与容量要求

| 指标 | 要求 |
|------|------|
| 规则评估延迟 | 从数据入库到规则判定 ≤ 5 秒（实时告警） |
| 数据质量告警 | 每日定时扫描，T+1 完成 |
| 告警推送延迟 | 弹窗/站内信 ≤ 3 秒，短信 ≤ 30 秒 |
| 告警存储 | 告警事件年增量约 720 万条，保留 12 个月 |
| 规则数量上限 | 支持 ≥ 500 条活跃规则同时在评估引擎中运行 |
| 告警并发推送 | 支持每秒 ≥ 100 条告警的推送吞吐 |

> **延迟指标说明**：规则评估延迟（≤ 5s）与仪表盘数据刷新（≤ 30s，详见 2.2 技术指标）是两个不同层级的指标。规则评估在消息与流处理层实时完成（数据到达即触发判定），仪表盘数据刷新是应用呈现层的定时轮询行为。两者互不冲突，分别面向告警实时性和展示性能两个维度的要求。

#### 3.8.9 技术依赖

告警规则引擎的实时评估需要以下基础设施支撑：

| 依赖组件 | 用途 | 建议方案 |
|---------|------|---------|
| 流处理引擎 | 实时数据流接入、规则评估、窗口聚合 | Kafka Streams / Flink |
| 消息队列 | 设备数据削峰填谷、告警事件异步通知 | Kafka / RabbitMQ |
| 短信网关 | High / Critical 级别告警短信通知 | 对接第三方短信服务 |
| 语音呼叫服务 | Critical 级别告警语音电话通知 | 对接云呼叫中心服务 |
| WebSocket 服务 | 告警弹窗实时推送到浏览器 | Spring WebSocket + STOMP |

> **规则引擎选型建议**：≤ 50 条简单阈值规则可使用自研条件匹配器（规则存入数据库循环扫描）；≥ 50 条规则或涉及基线/复合规则，建议引入轻量级规则引擎（EasyRules）或流处理框架的 CEP 能力。一期建议先以数据库轮询 + 简单条件判定实现，二期引入流处理引擎增强。
>
> **告警延迟与仪表盘刷新关系**：规则评估延迟（≤ 5s）与仪表盘数据刷新（≤ 30s，详见 2.2 技术指标）是两个不同层级的指标，并行存在、不冲突。规则评估在消息与流处理层实时完成（数据到达即触发判定），仪表盘数据刷新是应用呈现层的定时轮询行为，分别面向告警实时性和展示性能两个维度的要求。

### 3.9 对外 API 服务

> **说明**：对外 API 服务是跨模块通用能力，覆盖五大类资源的查询、空间分析和告警订阅，供第三方系统集成和上级平台数据上报使用。

当前文档定位为"为城市规划、应急指挥、公共服务提供数据底座"，但未定义对外暴露的标准 API。本节补充对外 API 服务规范，支持第三方系统集成和数据开放。

#### 3.9.1 接口分类

| 分类 | 说明 | 调用方示例 |
|------|------|-----------|
| **数据查询 API** | 按条件查询资源数据，返回 GeoJSON 格式 | 第三方系统、数据分析平台 |
| **空间分析 API** | 空间查询、缓冲区分析、路径规划等 | 应急指挥系统、智慧城市平台 |
| **告警订阅 API** | Webhook 方式推送告警事件 | 集成告警系统、短信通知平台 |
| **资源管理 API** | 资源数据的增删改查（需管理员权限） | 数据维护系统、移动采集端 |
| **统计报表 API** | 聚合统计和报表数据导出 | 上级平台数据上报 |

#### 3.9.2 接口规范

- **协议**：HTTPS + RESTful API，数据格式统一为 JSON
- **命名规则**：`/api/v1/{resourceType}/{action}`，版本号嵌入 URL
- **标准响应结构**：

```json
{
  "code": 200,
  "message": "success",
  "data": { ... },
  "timestamp": 1680000000000,
  "requestId": "uuid"
}
```

- **分页规范**：查询类接口统一支持 `page` / `size` / `sort` 参数，响应中返回 `total` / `totalPages` 元数据
- **空间数据格式**：统一使用 GeoJSON（RFC 7946），坐标参考 CGCS2000
- **日期格式**：ISO 8601（`yyyy-MM-dd'T'HH:mm:ss'Z'`）

#### 3.9.3 认证与鉴权

- **认证方式**：OAuth 2.0 Client Credentials 流程，调用方申请独立 AppKey + AppSecret
- **鉴权粒度**：按 API 分类授权，每个 AppKey 可独立配置可调用的 API 范围
- **频率限制**：默认 1000 次/小时/AppKey，超额返回 429 Too Many Requests
- **IP 白名单**：可选配置，仅允许指定 IP 段调用

#### 3.9.4 核心接口清单

| 接口路径 | 方法 | 说明 | 权限级别 |
|---------|------|------|---------|
| `/api/v1/buildings` | GET | 查询楼栋信息（支持空间过滤 bounding box） | 数据查询 |
| `/api/v1/buildings/{id}` | GET | 获取单栋楼栋详情 | 数据查询 |
| `/api/v1/manhole-covers` | GET | 查询井盖信息及状态 | 数据查询 |
| `/api/v1/cameras` | GET | 查询摄像头点位及状态 | 数据查询 |
| `/api/v1/air-quality` | GET | 查询空气质量监测站最新数据 | 数据查询 |
| `/api/v1/water-quality` | GET | 查询水质监测站最新数据 | 数据查询 |
| `/api/v1/spatial/within` | GET | 空间包含查询：指定 GeoJSON 多边形内的所有资源 | 空间分析 |
| `/api/v1/spatial/buffer` | GET | 缓冲区查询：指定点位 radius 米范围内的资源 | 空间分析 |
| `/api/v1/spatial/distance` | GET | 距离计算：两点之间的空间距离 | 空间分析 |

| `/api/v1/alerts/subscribe/{id}` | DELETE | 取消告警 Webhook 订阅 | 告警订阅 |
| `/api/v1/alerts` | GET | 查询告警事件列表 | 数据查询 |
| `/api/v1/stats/summary` | GET | 全局资源统计摘要（各类资源总数、告警数等） | 统计报表 |
| `/api/v1/stats/trends` | GET | 资源趋势数据（按日/周/月） | 统计报表 |
| `/api/v1/reports/upload` | POST | 现场巡查上报（拍照+定位+文字描述），移动端使用 | 资源管理 |

#### 3.9.5 接口稳定性保障

- **版本管理**：重大变更发布新版本（`/api/v2/...`），旧版本至少维护 6 个月
- **向下兼容**：新增字段不破坏已有响应结构；删除字段或修改字段类型视为 Breaking Change，必须发新版本
- **变更通知**：API 变更提前 30 天在接口文档和站内信中公告
- **沙箱环境**：提供独立的 API 沙箱环境（`sandbox-api.city-platform.com`），供第三方开发者调试

#### 3.9.6 接口文档

- **文档格式**：OpenAPI 3.0（Swagger）规范，自动生成在线文档
- **文档地址**：`/swagger-ui.html` 和 `/v3/api-docs`（Spring Boot 原生集成 SpringDoc）
- **测试工具**：Swagger UI 中直接发起请求测试

#### 3.9.7 性能与容量

| 指标 | 要求 |
|------|------|
| API 响应时间 | 简单查询 ≤ 200ms，空间分析 ≤ 2s |
| 并发连接数 | 单节点 ≥ 200 QPS |
| 可用性 | 核心 API（数据查询类）≥ 99.9% |
| 数据开放范围 | 一期开放五大类资源的**查询**和**空间分析**接口，管理和订阅接口视需求二期开放 |

## 5. 非功能性需求

### 5.1 性能需求

性能指标要求详见 [2.2 技术指标](#22-技术指标)，本节仅补充各指标的测量口径：

| 指标 | 测量口径说明 |
|------|-------------|
| 首屏加载 | 从页面 URL 输入到地图渲染完成、默认图层可见的耗时 |
| 瓦片加载 | 单次缩放/平移后新视口内所有瓦片加载完成的耗时 |
| 图层切换 | 从点击图层开关到该图层渲染完成的耗时 |
| 点位点击 | 从点击地图资源点位到信息卡片弹出的耗时 |
| 空间查询 | 从绘制查询范围到结果返回并地图高亮的耗时 |

### 5.2 可靠性

- 系统可用性 ≥ 99.9%（除计划内维护）
- 支持 7×24 小时不间断运行
- 单点故障不影响核心功能
- 数据每日自动备份，备份保留 ≥ 30 天

### 5.3 安全性

- 用户认证：统一身份认证（OAuth2.0/LDAP）
- 权限控制：基于 RBAC 的图层级和数据级权限管理
- 操作审计：所有用户操作全日志记录，可追溯
- 数据安全：敏感数据（人口信息等）加密存储，脱敏展示
- 防篡改：重要数据增删改操作需审批流程

### 5.4 可扩展性

- 资源类型可配置：支持新增资源类型，无需修改核心代码
- 数据源可接入：支持 REST API、WebSocket、MQTT、JDBC 等多种接入方式
- 图层插件化：每个资源图层为独立插件，可独立开发部署
- 地图引擎可替换：CesiumJS 封装为标准地图引擎接口（MapEngineAdapter），支持 3D / Columbus View / 2D 视图模式切换；如需替换为其他引擎（如 Mapbox GL JS），仅需实现相同接口适配层

### 5.5 数据隐私与安全合规

#### 5.5.1 数据分级

| 级别 | 定义 | 范围 | 展示规则 |
|------|------|------|---------|
| L1-公开 | 不涉及个人身份信息 | 楼栋轮廓、道路、绿地、空气质量指数 | 正常展示 |
| L2-内部 | 脱敏后可展示 | 摄像头点位、网格员姓名（脱敏电话）、楼栋入驻率 | 脱敏后展示 |
| L3-敏感 | 严格权限控制 | 实有人口详情、特殊人群分类、通行记录、人脸图片 | 仅授权角色查看，操作全审计 |

#### 5.5.2 数据脱敏规则

| 字段 | 脱敏规则 | 示例 |
|------|---------|------|
| 姓名 | 保留姓氏，其余 `*` 代替 | 张** |
| 手机号 | 中间 4 位隐藏 | 138****5678 |
| 身份证号 | 保留前 6 位和后 4 位 | 110101********1234 |
| 具体地址 | 保留到小区/楼栋级 | **小区 **栋 |
| 人脸图片 | 传输和存储全链路加密 | — |

#### 5.5.3 访问控制

- **统一认证**：OAuth2.0 + LDAP，支持密码+短信双因素
- **三域权限模型**：图层域（能看到哪些资源类型）/ 数据域（能看到哪些行政区域）/ 操作域（只读/导出/编辑/管理）
- **全量审计**：L3 数据的每次查看和操作，记录"谁 + 何时 + 查了谁 + 操作类型"

#### 5.5.4 合规要求

- 遵循《个人信息保护法》《数据安全法》《网络安全法》
- 系统需通过等保 2.0 二级及以上测评
- 人脸数据需单独取得用户授权同意
- 数据导出需审批 + 水印 + 自动审计日志

## 6. 数据架构

### 6.1 数据分层

| 层级 | 内容 | 更新频率 |
|------|------|---------|
| 基础地理数据 | 行政区划、道路网、水系、遥感影像 | 按需更新 |
| 资源静态数据 | 楼栋、桥梁、管网、摄像头等基础属性 | T+1 |
| 资源动态数据 | 设备状态、实时监测值、告警事件 | ≤ 30 秒 |
| 业务关联数据 | 人员、企业、工单、巡检记录 | T+1 / 实时 |
| 统计数据 | 聚合统计、指标计算、分析结果 | 按调度策略 |

### 6.2 空间数据格式

- **坐标系**：CGCS2000（国家大地坐标系），前端瓦片使用 Web Mercator（EPSG:3857）
- **数据格式**：所有空间数据以 GeoJSON 作为交换格式，内部存储使用 PostGIS 的 GeoJSON 字段（geometry 类型）
- **瓦片服务**：矢量瓦片（MVT 格式）和栅格瓦片（PNG/WebP）

### 6.3 数据接入要求

- 已有系统优先通过 API 对接（避免重复录入）
- 无系统数据提供标准 Excel/CSV 导入模板
- IoT 设备数据通过 MQTT/CoAP 接入，需定义统一 JSON 数据格式规范和 MQTT Topic 命名规则（如 `/city-rag/{resourceType}/{deviceId}/telemetry`）
- 所有数据接入需经过清洗、校验、空间化处理

### 6.5 数据治理

#### 6.5.1 数据责任矩阵

| 数据域 | 源头部门 | 数据质量责任人 | 更新周期 |
|--------|---------|--------------|---------|
| 建筑数据 | 住建局 / 自然资源局 | 指定专人 | T+1 |
| 市政数据 | 城管局 / 市政工程处 | 指定专人 | T+1 / 实时 |
| 安防数据 | 公安局 / 政法委 | 指定专人 | 实时 |
| 生态数据 | 生态环境局 | 指定专人 | 实时（监测站） |

| 网格数据 | 政法委 / 街道办 | 指定专人 | 按需调整 |

#### 6.5.2 权威数据源认定

多源数据冲突时按以下优先级认定权威数据源：

1. **人口数据**：公安局户籍系统 > 街道办登记 > 网格员摸排
2. **建筑数据**：不动产登记数据 > 规划审批数据 > 现场测绘
3. **企业数据**：市场监管局注册数据 > 街道办统计 > 物业登记
4. **设备数据**：IoT 平台实时数据 > 资产管理系统 > 人工台账

#### 6.5.3 数据质量监控

- **完整性检查**：每日扫描必填字段空值率，超阈值自动告警
- **时效性检查**：数据更新时间超过预设周期触发督办流程
- **一致性检查**：多源数据交叉比对，差异自动上报
- **质量看板**：按数据域展示数据质量评分及趋势

## 7. 实施建议

### 7.1 技术选型建议

| 层级 | 推荐技术 |
|------|---------|
| 地图引擎 | CesiumJS |
| 前端框架 | React + TypeScript |
| 后端服务 | Java Spring Boot |
| 空间数据库 | PostgreSQL + PostGIS |
| 时序数据 | InfluxDB |
| 瓦片服务 | TiandiMap / 自建 MVT 瓦片 |
| 消息队列 | RabbitMQ / Kafka（设备数据接入） |
| 可视化库 | ECharts / Deck.gl / D3.js |

> **后端说明**：后端统一采用 Java Spring Boot 3.x + JDK 17 技术栈。构建工具使用 Maven，ORM 框架使用 MyBatis-Plus（空间数据查询配合 PostGIS 扩展），接口规范遵循 RESTful API + WebSocket（实时推送）。Spring Cloud 微服务体系视项目规模决定是否引入，一期建议单体应用 + 模块化分包，二期按需拆分。
>
> **地图引擎说明**：统一采用 CesiumJS 作为地图引擎，利用其视图模式切换（3D / Columbus View / 2D）适配不同使用场景。CesiumJS 原生支持 3D Tiles 倾斜摄影模型加载，适合未来城市级数字孪生扩展。若后期需要轻量化纯 2D 场景，可通过 MapEngineAdapter 接口适配其他引擎。

### 7.2 Phase 划分建议

| Phase | 内容 | 建议工期 |
|-------|------|---------|
| Phase 1 | CesiumJS 初始化 + Spring Boot 项目脚手架搭建 + 底图接入 + 通用交互能力 + 告警规则引擎骨架 + 对外 API 框架（Swagger + OAuth2 认证） | 4 周 |
| Phase 2 | 建筑资源模块（含三维白模） | 3 周 |
| Phase 3 | 市政资源模块 | 4 周 |
| Phase 4 | 安防资源模块 | 3 周 |
| Phase 5 | 生态资源模块 | 3 周 |
| Phase 6 | 人口与网格资源模块 | 3 周 |
| Phase 7 | 跨模块综合大屏 + 全局报表 + 领导驾驶舱 | 2 周 |
| Phase 8 | 联调测试 + 性能优化 + 上线 | 2 周 |

> **Phase 职责说明**：各模块内部的统计仪表盘（统计卡片、趋势图、排行榜等）分别在 Phase 2-6 各自模块开发时完成。Phase 7 仅负责跨模块的综合大屏整合和全局性报表，不重复建设模块内仪表盘。
>
> **投入模式说明**：Phase 1 前后端并行开发（前端 CesiumJS + 后端 Spring Boot），Phase 2-6 建议前端 1-2 人 + 后端 1 人按模块推进，Phase 7-8 全员集中联调。总工期约 23 周（~6 个月）。
>
> **API 实施说明**：Phase 1 搭建对外 API 框架（Swagger 集成 + OAuth2 认证 + 通用分页/异常处理），完成框架代码但不实现具体业务接口。Phase 2-6 在各模块开发时同步实现对应资源的 REST API（如 Phase 2 实现 `/api/v1/buildings`，Phase 3 实现 `/api/v1/manhole-covers` 等），并编写 OpenAPI 文档注解。

### 7.3 数据准备建议

1. **优先对接已有系统**：梳理各委办局（住建局、城管局、公安局、环保局、街道办）现有系统和数据接口
2. **数据质量评估**：对现有数据进行完整性、准确性、时效性评估，制定数据治理计划
3. **空间化处理**：所有资源数据需要空间化（坐标采集、地址编码、GIS 配图）
4. **数据标准制定**：统一资源编码体系、属性字段标准、坐标标准
5. **更新机制建立**：明确各类数据的更新责任部门和更新周期

### 7.4 风险识别与应对

| 风险项 | 影响 | 概率 | 缓解措施 |
|-------|------|------|---------|
| 委办局数据不开放或接口不可用 | 关键资源数据缺失，系统无法上线 | 高 | 提前签署数据共享协议；准备 Excel/CSV 离线导入兜底方案 |
| 基础地理数据精度不足 | 建筑轮廓偏移、点位位置不准 | 中 | 预留空间校正工期；评估购买商业高精度地图数据 |
| 三维渲染性能不达标 | 浏览器卡顿、帧率低，用户体验差 | 中 | 设置 LOD 分级策略；3D 视图帧率 < 15fps 自动切换为 Columbus View / 2D 模式；WebGL 不可用时降级 Canvas 2D 点位标注 |
| IoT 设备数据量大、写入压力高 | 数据库写入瓶颈，数据延迟 | 中 | 引入消息队列削峰填谷；时序库采用列式存储压缩 |
| 用户权限管理复杂 | 权限配置混乱，数据泄露风险 | 中 | 严格三域权限模型；上线前进行权限渗透测试 |
| 多源数据冲突 | 同一数据不同来源不一致，可信度降低 | 高 | 按 6.5.2 权威数据源规则认定；差异数据自动上报仲裁 |
| 项目延期 / 资源不足 | Phase 无法按时交付 | 中 | 核心 Phase（1+2）优先保障；非核心功能二期迭代 |
